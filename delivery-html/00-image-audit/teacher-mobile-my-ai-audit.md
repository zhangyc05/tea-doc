# 第 0 步第四批｜教师端我的 / AI 助手模块图片内容校验

> 分支：`delivery-html-business-prototype`  
> 范围：`效果图/教师手机端/3我的/`、`效果图/教师手机端/4AI助手/`  
> 目标：校验教师端“我的”和“AI 助手”相关效果图的真实页面归属，明确后续 HTML 原型是否进入首批、如何与成长档案、能力画像、岗位/聘期对照和个人发展报告闭环衔接。

## 1. 校验口径

本批次继续坚持：**不直接相信文件名，先按业务对象和页面功能归类**。

判断顺序：

1. 页面是否属于底部 Tab「我的」或中间悬浮「AI 助理」；
2. 页面业务对象是个人主页、能力画像、画像依据、目标岗位、聘期要求、发展报告，还是 AI 补充档案；
3. 页面是否引用成长档案中的正式事实；
4. 页面是否可能改变档案数据状态；
5. AI 是否越权，例如自动确认、自动归档、自动形成评价结论；
6. 是否与教师端档案、活动、待办存在重复。

> 当前 GitHub 连接器对 PNG 二进制内容无法稳定直接渲染，因此本批次先基于仓库路径、文件名线索和前期已确认的产品口径做结构化校验。后续进入 HTML 前，如发现图片真实内容与本表不一致，再按视觉复核结果修正。

## 4. 本批次产品取舍决策

| 问题 | 决策 | 后续执行方式 |

| 我的能力画像采用哪个版本 | 采用 `我的能力画像-版本二.png` | 版本一作为候选历史版本，不进入首批 HTML |

| AI 是否可自动入档 | 不可以 | AI 只能整理草稿；教师提交后进入待确认 / 待核验 |

## 6. 页面业务说明要求

后续 HTML 页面中，每个页面都应加入业务说明区：

1. **我的能力画像**  
   - 画像基于正式档案事实生成；
   - 不是评价结论；
   - 四轴为教学、教研、实践、服务；
   - 基本能力只作为中心达标徽章；
   - 展示“教学实践型教师”等发展特征时，应说明是基于结构推断的解释性标签。

2. **画像用到的记录**  
   - 只展示正式档案事实；
   - 说明每条记录支撑哪个能力维度；
   - 不展示待确认、线索、草稿记录。

3. **目标岗位对照**  
   - 当前岗位已达成时不做对照；
   - 只展示目标岗位要求与当前已入档依据之间的差距；
   - 操作入口应指向已有业务，如补充档案、培训需求、企业实践、教研活动。

4. **聘期要求对照**  
   - 使用教师可理解文案；
   - 避免“通过 / 不通过”压力表达；
   - 明确哪些依据已入档，哪些可补充。

5. **个人发展报告**  
   - 详情页直接展示报告正文；
   - 需要图文并茂，不做纯摘要页；
   - AI 可生成报告草稿，但不自动形成正式评价。

6. **AI 补充档案**  
   - AI 负责整理材料、提取字段、生成提交草稿；
   - 教师确认后提交；
   - 提交后进入待核验或待确认，不自动正式入档。

## 8. 暂不明确的缺口

1. `我的发展报告.png` 需要后续视觉复核判断它是列表页还是详情页；HTML 阶段要补齐缺失的另一种形态。

3. 我的主页中是否承接“系统设置 / 个人资料”类页面，当前不进入首批，避免扩大范围。
